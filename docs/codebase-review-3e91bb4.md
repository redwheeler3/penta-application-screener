# Codebase review of 3e91bb4

November 25, 2026. Five open findings. Fix the email-change retry and income entry first. The first can disclose a later mailbox to an earlier one. The second can change a fact used in eligibility decisions.

## Findings

1. **A delayed email-change notice names the wrong new address.** When A changes to B, the notice addressed to A records only A in its retry intent. If B subsequently changes to C, the retry builds A's notice from the application's current email. In an in-memory probe with two quota failures, the real outbox sent captured notices to both A and B saying the change was to C. With only A → B, A correctly received B. This also discloses C to A even though those addresses were never the endpoints of the same change. Capture both endpoints of each confirmed transition when staging its notice and render retries from those facts. For already queued notices lacking the destination, use a generic change notice rather than guessing an address. Keep the established cleanup of successful retry intents. Acceptance should cover both transitions, delayed delivery and old-format intents. This needs no extra provider call. [Notice producer](../backend/app/services/email/transactional.py) · [Retry intent](../backend/app/services/email/retry_intents.py) · [Outbox](../backend/app/services/email/outbox.py) · [Security notice template](../backend/app/services/email/templates/access.py)

2. **Pasting an income range produces a valid multibillion-dollar income.** The shared number control strips separators and interior minus signs before the income validator sees the input. In the actual applicant component, pasting `60,000–65,000` produced `6000065000`, passed field validity, went into the working-save request and reached declaration review. The submission schema separately accepted that integer. The control input `65,000.00` correctly produced `65000`. A mistaken paste can therefore feed the wrong household total into a member's income rule. Preserve invalid input long enough to explain “Enter one whole-dollar amount” and let the applicant correct it. Normalize only unambiguous formats. Keep blank, zero and supported decimals working for their respective consumers. Test the saved payload as well as the visible value. No new dependency or server request is needed. [Number input](../frontend/src/components/shared/NumberInput.tsx) · [Applicant field validation](../frontend/src/applicant/ApplicantFormFields.tsx) · [Submission answers](../backend/app/schemas/applicant/answers.py) · [Eligibility filters](../backend/app/domain/hard_filters.py)

3. **Declaration review admits answers submission will refuse.** Two otherwise complete fictional forms reached “Submit application” after a mocked successful private save. One had three spaces as the required “Why a co-op” essay. The other had a current move-in date of June 1, 2025 and previous move-in dates of August 1, 2025 and January 1, 2024, in that order. The actual submission contract rejected the first as missing and the second for residence order. The valid control passed. The review step checks native field validity, which accepts spaces in required text and checks each date independently. Add trimmed-required checks and strict adjacent-date ordering at review, identify the offending field, and preserve the ability to save an unfinished private draft. Reuse the existing validation pass. Test each bad form and its corrected version through review and the submission schema. [Review admission](../frontend/src/applicant/ApplicantApp.tsx) · [Form validation](../frontend/src/applicant/ApplicantFormFields.tsx) · [Submission completeness](../backend/app/schemas/applicant/submission.py) · [Residence ordering](../backend/app/schemas/applicant/answers.py)

4. **A note-only eval edit can undo another editor's grading change.** Starting with two copies of the same scoring case, one editor saved a new minimum score of 0.8. A second editor changed only the note on their earlier copy. Both saves succeeded against a temporary fixture. The second note survived, but the original neutral band and confidence requirement replaced the first editor's new label. The recent duplicate-create fix protects new keys. For existing keys, compare the editor's original case with the current case under the existing fixture lock before replacing it. Return a conflict that preserves the draft when they differ. Compare the whole stored case because the grading fingerprint deliberately excludes editorial fields. Test two tabs, edits to different keys, and Judge-tab routing. This can use the file read already required for saving. [Case editor](../frontend/src/components/evals/EvalCaseEditor.tsx) · [Save request](../frontend/src/components/evals/RunnableEval.tsx) · [Fixture writer](../backend/app/evals/case_store.py) · [Grading fingerprint](../backend/app/evals/dataset.py)

5. **Latest-run harvest commands load every matching historical analysis.** With 100 analyses in SQLite, an ORM load listener counted 100 constructed analysis objects for the shared harvest helper, and 100 for the categorical CLI scoped to one opening. The existing ranking service returned the same newest ID while loading one object. Both harvest queries call Python-side `.first()` without SQL `LIMIT 1`. Reuse `get_latest_analysis` in the global helper and `get_current_analysis` for the opening-specific command. Keep their respective synthetic checks and preserve the no-run case. This is a measured operator-tool inefficiency. No production latency estimate is implied.
