# Open findings from the review of f779db2

November 25, 2026. Four passes covered applicant and committee journeys, shared data and its consumers, failure and completion order, and a final check against controls and prior findings. All five issues below were reproduced on the same application baseline. Start with daily maintenance and applicant date validation.

## Findings

1. **Two daily email sweeps can run together across Pacific midnight.** Maintenance checks ownership against a row keyed by task and date. A live worker can keep renewing yesterday's row while a new request claims today's row. In an in-memory test, five fictional notices took two simulated seconds per retryable failure. Starting four seconds before midnight and issuing a second request during send three produced nine provider attempts. Both daily runs reported completion. The final two recipients were each attempted twice after midnight, seconds apart. Moving the identical sequence one hour later produced five attempts and a single owner. No message was accepted in this test. Make daily acquisition atomically defer to any unexpired running owner for the same task, including yesterday's. Keep daily completion records and the existing per-delivery guards. Verify both start times and recovery of a previous-day owner after its lease expires. This adds a bounded database check at acquisition and no work per recipient. [Maintenance](../backend/app/services/maintenance.py) · [Outbox](../backend/app/services/email/outbox.py)

2. **The actual form rejects a date the server already accepts.** At `2026-11-25T07:30:00Z`, the installed JavaScript runtime computed November 24 for Vancouver. The actual form field set its maximum to November 24 and failed validity for a November 25 employment start. At that same instant, the backend's Vancouver clock returned November 25 and its employment schema accepted the date. The clocks agreed at 06:30 and 08:30 UTC. The earlier browser-local timezone fix is present. The remaining difference comes from the two runtimes' timezone data, and the existing frontend test hardcodes a winter boundary that disagrees with the installed backend. Make the server authoritative for the date used by the applicant form. For example, include the Pacific date and its next change in the existing applicant bootstrap/lifecycle responses, refresh at that boundary and on resume, and use the value for both the field maximum and review validation. Test the same instants through both consumers, including a form left open over midnight. This avoids a separate request on initial load. The discrepancy was measured locally and can vary with the user's browser. [Frontend date helper](../frontend/src/format.tsx) · [Form validation](../frontend/src/applicant/ApplicantFormFields.tsx) · [Server calendar](../backend/app/core/time.py) · [Existing boundary tests](../frontend/src/applicant/ApplicantFormFields.test.tsx)

3. **Opening confirmation checks the total but can send a different message than previewed.** The admin sees counts by email variant. In an isolated HTTP probe, preview showed one notification-list email. The same mailbox then acquired a qualifying retained application, changing the preview to one combined application-and-list email. Publishing with the original confirmation returned HTTP 200 and queued an application-opening intent. The total and recipient were identical throughout. Compare the three displayed variant counts under the existing publication lock and require a fresh preview if any changed. Use those same counts for the total. Verify a counts-preserving change of variant, an unchanged preview, and a retry after successful publication. No recipient identities, extra queries or additional success-path round trip are needed. [Confirmation panel](../frontend/src/components/admin/OpeningLaunchPanel.tsx) · [Publication route](../backend/app/api/openings.py) · [Audience and templates](../backend/app/services/openings/vacancy_notifications.py)

4. **“Add case” can replace an existing eval case and its grading label.** The editor knows whether it is creating or editing, but sends the same save request for both. With a temporary copy of the scoring fixture, saving a new draft under an existing key kept the case count at one and replaced the original neutral scoring band and confidence requirement with a minimum score of 0.9. This can silently change what subsequent eval runs count as passing. Carry create versus edit intent to the existing locked fixture writer. On creation, refuse an occupied key and leave the draft available. Keep intentional edits working, including edits routed from the Judge tab. Verify duplicate creates, competing creates and deliberate edits against a temporary file. The check reuses the lookup the writer already performs. This concerns local fixture editing. [Editor](../frontend/src/components/evals/EvalCaseEditor.tsx) · [Save path](../frontend/src/components/evals/RunnableEval.tsx) · [Fixture writer](../backend/app/evals/case_store.py)

5. **A disconnected Fly response body bypasses the watchdog's lookup retry.** The retry covers fetching the response headers. The watchdog reads the body afterward. A simulated HTTP 200 whose body stream disconnected produced one lookup and one immediate webhook alert on the first alarm. The next alarm was scheduled normally. Read the response body within the existing transient lookup retry and feed exhausted transport failures into the existing two-poll confirmation. Keep configuration and machine-selection errors on their immediate reporting path. Check a body failure followed by success and two polls of exhausted body reads. Healthy polls incur no extra request. [Watchdog](../ops/fly-watchdog/src/index.ts) · [Retry policy](../ops/fly-watchdog/README.md)
