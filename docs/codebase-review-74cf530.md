# Codebase review of 74cf530

Reviewed November 24, 2026. All five findings below describe the original baseline and have been fixed.

Rank now captures history and source identities in one SQLite snapshot before its first progress
event. The final retention check prevents a concurrent purge from republishing erased text.
Ranking views and feedback endpoints also enforce expiry before physical deletion. The feedback
composer displays and retains its original applicant through navigation and retry. The categorical
harvester checks synthetic provenance before printing candidates, and an incomplete SocketLabs
page returns the existing unavailable status.

Verification passed with 1,388 backend tests, one skip, 496 frontend tests, lint and the frontend
production build. A live Bedrock Rank using two fictional applications produced 13 criteria,
scored both applicants and completed consolidation with zero failures. Recorded cost was $0.0836.

## Findings

1. **Rank can republish an erased explanation.** The criteria stream reads historical criterion text, yields its first progress event, then captures the IDs that will be checked at publication. In an isolated SQLite run with two fictional applicants, a second session purged the historical contributor during that interval. The current criteria endpoint immediately stopped returning its marker. Resuming the real stream with the mock provider published a new analysis containing the marker and only the surviving applicant's ID. The final retention check therefore passed. Capture historical text and its source IDs in the same short database snapshot before yielding or starting workers. Reuse that snapshot for matching and the existing publication check. Verify purge before capture, between capture and publication, and after publication. No database lock needs to span a provider call. [Criteria stream](../backend/app/services/ranking/pipeline.py) · [Source capture](../backend/app/services/ranking/provenance.py) · [Adoption of prior text](../backend/app/services/ranking/identity.py)

2. **A feedback draft changes applicant when the reviewer navigates.** The workspace keeps the composer mounted. Its text survives navigation, but Send takes the applicant from the currently displayed page. In two component probes a reviewer typed a fictional quote on applicant A, navigated, then sent. The same text was submitted with a null applicant on a general page and with B's ID on B's page. Both are valid submission contexts. A's eventual purge would miss the quote. Capture the review context when opening the composer, show which applicant the draft concerns, and keep using that context on retry. Test both navigation cases and rejection if A disappears. This uses the existing IDs and submission endpoint. [Workspace](../frontend/src/CommitteeWorkspace.tsx) · [Composer](../frontend/src/components/shared/FeedbackButton.tsx) · [Feedback persistence](../backend/app/services/feedback.py)

3. **Expired applicant text remains readable until physical purge.** With one retained participant keeping an opening visible, a second contributor reached its Pacific expiry. Before the sweep, the authenticated current-criteria response still contained its marked pool explanation, and the admin feedback response still contained its marked feedback body. After purge both responses omitted the marker. The feedback projection filters the link and name but emits the stored body. Ranking checks opening visibility and returns the stored explanation. Apply the existing retention predicate to these text projections, including the board and operator traces that share the underlying material. Preserve generic criteria and general feedback. Batch source checks per response and test the expiry/protection boundaries before and after sweep. This read-time issue is independent of the publication race in finding 1. [Feedback projection](../backend/app/api/feedback.py) · [Ranking presentation](../backend/app/api/ranking/presentation.py) · [Trace routes](../backend/app/api/ranking/current.py) · [Retention policy](../backend/app/services/applications/retention.py)

4. **The manual categorical eval harvester copies unverified free text into fixture candidates.** The CLI copies the stored decomposition decision into the proposed label rationale. Running its real entry point against an uncertified synthetic test analysis printed a fictional decision marker twice, once for decomposition and once for matching. It prompts the operator to commit the candidates. This probe establishes a path into proposed fixtures, not an actual disclosure or commit. Apply the existing synthetic guard before emitting audit prose, or emit descriptors without the rationale on unverified runs. Check both output modes, unknown history and certified inputs. No extra model call or new classifier is needed. [CLI](../backend/scripts/harvest_golden_cases.py) · [Existing guard](../backend/app/evals/synthetic_guard.py)

5. **An incomplete SocketLabs report can appear as an empty queue.** The queue reader accepts an empty page even if the response advertises more rows. With a mock HTTP transport, both an empty report with total zero and an empty page with total twelve yielded an available count of zero. The admin panel then says “No messages are waiting at SocketLabs.” The twelve rows are report rows whose delivery states are unknown. Return the existing unavailable result when pagination ends early, so an incomplete refresh cannot replace a previously valid observation. Test a genuinely empty report, a missing first page and a missing later page. This needs one count comparison and no additional network calls. The inconsistent upstream response was simulated. [Queue reader](../backend/app/services/email/socketlabs_queue.py) · [Admin display](../frontend/src/components/admin/EmailDeliveryPanel.tsx)
